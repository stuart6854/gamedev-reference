# Modules and plugins

As an engine grows, it splits into modules: core, rendering, physics, audio, the editor, and the game itself. A module system decides how they find each other, the order they start in, and whether they are compiled in or loaded from a library at run time.

## The module interface

```text
Module {
    name
    dependencies[]                  // module names
    startup(engine)                 // register systems, components, asset loaders, editor panels
    shutdown(engine)
}
```

`startup` is where a module plugs into the rest of the engine: a physics module registers its systems in the [frame phases](frame.md#phases), its component types with the ECS, and its asset types with the [resource system](resources.md). The engine core knows nothing about physics; it only knows how to run registered systems.

Modules start in dependency order and shut down in reverse, exactly like [subsystems](subsystems.md#lifetime-and-order). Report a missing dependency or a cycle at start-up, by name.

## Layers

```text
Core           containers, maths, memory, logging, file system, jobs
Platform       window, input devices, threads, time
Renderer, Audio, Physics, Assets      (each depends on Core and Platform)
Gameplay framework                    (scenes, ECS, scripting)
Game modules
Editor modules (depend on everything above; nothing depends on them)
```

Dependencies only point down. When a lower module needs to call up (the renderer wants to draw the editor's gizmos), it defines an interface or a callback, and the higher module provides it. Enforce the direction in the build: if `Renderer` does not link `Editor`, it cannot include its headers by accident.

## Static plugins

Compiled into the executable. The engine still needs a list of them, and two ways are common:

```cpp
// 1. An explicit list, written by hand or generated by the build system.
void register_modules(ModuleRegistry& r)
{
    r.add<CoreModule>();
    r.add<RenderModule>();
    r.add<PhysicsModule>();
    r.add<GameModule>();
}

// 2. Self-registration through a static object in each module.
static ModuleRegistrar<PhysicsModule> s_physics_registrar;    // constructor adds it to a global list
```

Self-registration looks tidier, but has two traps. Static constructors run in an unspecified order, so the global list must be created on first use (a function-local static), not as a global. And a linker building a static library drops object files that nothing references, taking the registrar with it, so the module silently disappears. Explicit lists, generated by the build system, avoid both.

## Dynamic plugins

Loaded from a shared library (`.dll`, `.so`, `.dylib`) at run time. Useful for optional modules, for mods, and for reloading game code without restarting.

```cpp
// In the plugin. extern "C" stops name mangling, so the host can find the symbol by name.
extern "C" PLUGIN_API Module* create_module(const EngineApi* api, uint32_t api_version);
extern "C" PLUGIN_API void destroy_module(Module* module);

// In the host
void* lib = load_library("Physics.dll");                         // LoadLibrary / dlopen
auto create = (CreateFn)find_symbol(lib, "create_module");       // GetProcAddress / dlsym
Module* m = create(&engine_api, ENGINE_API_VERSION);
```

- **The boundary is an ABI, not just an API.** C++ classes, `std::string`, and `std::vector` only work across it if both sides use the same compiler, the same standard library, and the same build settings. Either guarantee that (build engine and plugins together), or pass only C types: plain structs, function pointers, and handles.
- **Memory is freed by whoever allocated it.** On Windows each DLL can have its own heap, so memory from `new` in a plugin and `delete` in the host can crash. Give the plugin `destroy_module`, or pass it an allocator from the host.
- **Check the version.** The host passes `api_version`; a plugin built against a different version refuses to load, with a message, instead of calling functions that have moved.
- **The engine API** a plugin receives is a struct of function pointers (`EngineApi`), not the engine's headers. The plugin depends only on that struct, and the engine can change everything else.

## Reloading code

Reloading game code from a dynamic library while the game runs:

```text
reload(plugin):
    plugin.module.shutdown(engine)          // unregister systems, release resources
    destroy_module(plugin.module)
    unload_library(plugin.lib)
    copy Game.dll to Game_loaded_N.dll      // the compiler can overwrite the original
    plugin.lib = load_library("Game_loaded_N.dll")
    plugin.module = create_module(...)
    plugin.module.startup(engine)
```

- **State must live outside the library.** Anything in the plugin's globals or statics is gone after unloading. Keep game state in memory the host owns: the ECS world, or a block of memory the host allocates and hands to the plugin each time it loads.
- **Layouts may change between builds.** If a component gained a field, the state in host memory no longer matches. Either restart when layouts change, or keep enough type information (field names and offsets) to migrate data, like a save file.
- **Nothing may keep a pointer into the old library**: function pointers in event listeners, vtables of objects it created, strings in its read-only data. Unregistering everything in `shutdown` is what makes unloading safe.
- **Copy before loading**, because Windows locks a loaded DLL and the compiler cannot overwrite it. The PDB is locked too; give the copied DLL a fresh PDB path, or debugging breaks after the first reload.

For C# game code, a collectible `AssemblyLoadContext` plays the same role; see [hosting from C++](../../csharp/assemblies/hosting.md#reloading-scripts).

## Editor and runtime

The editor is the engine plus tools. Keep the tools out of the shipped game:

- **Separate modules.** `PhysicsEditor` depends on `Physics`; `Physics` never depends on `PhysicsEditor`. The shipped build does not link editor modules at all.
- **Editor-only data** (names, comments, thumbnails, source file paths) is stored in the authoring format and stripped when assets are **cooked** into the runtime format. The game loads only cooked data.
- **One code path for the game.** The editor runs the game by starting the same modules the shipped game uses, with editor modules added around them. If "play in editor" goes through different code, bugs only appear in shipped builds.
- **Build configurations** follow the same split: Debug and Development builds include the editor and debug tools; Shipping builds include neither, and compile out logging and checks.
